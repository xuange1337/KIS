# АРМ менеджера по работе с клиентами в CRM-системе

Web-приложение для ведения клиентской базы, планирования коммуникаций и
контроля сделок отдела продаж. Реализовано по описанию прикладной программы
(Орлов Г.Н., 23ФИИТ(б)РАИС).

Приложение закрывает все пять модулей из раздела 1.2 ТЗ, пять отчётов из
раздела 2.4 и набор экранных форм из раздела 2.5.

## Технологический стек

| Слой | Реализация |
|---|---|
| Клиент | React 18 + TypeScript, Vite, MUI 6, TanStack Query, Recharts |
| Сервер | NestJS 11 + TypeORM, JWT-авторизация, ролевая модель |
| База данных | PostgreSQL 17, схема ведётся миграциями |
| Выгрузки | CSV, Excel (exceljs), PDF (pdfmake, шрифт DejaVu с кириллицей) |
| Развёртывание | Docker Compose: `db`, `api`, `web` (nginx + reverse-proxy) |
| Защита | JWT с обязательными секретами, ограничение частоты входов, журнал действий, заголовки безопасности и CSP |

## Быстрый запуск

```bash
cp .env.example .env
```

Задайте в `.env` пароль базы и два секрета подписи токенов — значений по
умолчанию у них нет, без них приложение не стартует:

```bash
printf 'JWT_ACCESS_SECRET=%s\nJWT_REFRESH_SECRET=%s\nPOSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" "$(openssl rand -hex 16)"
```

```bash
docker compose up --build -d
```

Приложение поднимется на <http://localhost:8080>. Миграции применяются
автоматически при старте контейнера `api`.

Наполнение демонстрационными данными (20 клиентов, 32 сделки, 70 активностей,
14 коммерческих предложений):

```bash
docker compose exec api node dist/database/seeds/seed.js
```

Остановка с удалением данных:

```bash
docker compose down -v
```

## Тесты

```bash
POSTGRES_HOST=localhost npm run test:api
```

```bash
npm run test:web
```

E2E-тесты сервера (82 проверки) покрывают авторизацию и разграничение прав,
попытки обхода доступа между менеджерами, CRUD всех модулей, переходы сделки
по стадиям с записью в историю и защиту от гонок, границы числовых значений
и удаление связанных записей, расчёт всех пяти отчётов, разделение валют,
границы периодов и выгрузку в трёх форматах.

Тесты работают с отдельной базой `crm_test`: она пересоздаётся и наполняется
перед каждым прогоном (`server/test/global-setup.ts`), поэтому демонстрационные
данные не портятся, а результат не зависит от порядка выполнения.

## Принятые решения

**Разграничение доступа.** Менеджер видит только записи, где он указан
ответственным (`owner_user_id`); руководитель и администратор — данные всего
отдела. Условие задано один раз в `server/src/common/helpers/owner-scope.ts`
и применяется всеми модулями, включая отчёты. Права на вложенные сущности
наследуются от родителя: активность нельзя привязать к чужой сделке или к
сделке другого клиента, предложение — к чужой сделке.

**Секреты.** `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` обязательны и не имеют
значений по умолчанию: приложение и `docker compose` отказываются стартовать,
пока они не заданы, и проверяют минимальную длину. Иначе токены подписывались
бы ключом, известным всем, кто видел исходники.

**Сессии.** Refresh-токены привязаны к серверным сессиям и хранятся в базе
только в виде SHA-256-хеша. При обновлении токен ротируется, повторное
использование старого токена отзывает сессию. Выход, смена пароля и блокировка
пользователя также отзывают сессии. Refresh и logout защищены CSRF-токеном.

**История сделки.** Стадия меняется отдельной операцией
`PATCH /api/deals/:id/stage`: строка блокируется на запись, текущая стадия
читается внутри транзакции, обновление сделки и запись в `deal_stage_history`
выполняются вместе. Параллельные переводы не создают расходящихся записей.
Переход на стадию «выиграна» или «проиграна» проставляет дату закрытия,
возврат в работу — снимает её. Вероятность определяется стадией и напрямую
не редактируется.

**Удаление связанных записей.** Удаление клиента или сделки уносит по каскаду
контакты, активности, предложения и историю стадий, поэтому операция сначала
отвечает `409` с перечнем того, что будет потеряно, и выполняется только с
подтверждением: `DELETE /api/clients/:id?force=true`. Клиента со сделками
удалить нельзя вовсе — его переводят в архив.

**Валюты.** Курсы в прототипе не хранятся, поэтому суммы разных валют не
складываются: денежные отчёты считаются по одной валюте (параметр `currency`,
по умолчанию рубли), а в списках и карточках сумма выводится в валюте самой
сделки.

**Часовой пояс.** Деловой часовой пояс задаётся переменной `TZ`
(по умолчанию `Europe/Moscow`) и применяется и к серверу приложений, и к
соединению с СУБД. В нём считаются границы периодов в отчётах, группировка
по месяцам и признак просроченной активности — иначе они расходились бы с
тем, что видит пользователь.

**Журналирование.** Все изменяющие запросы, входы в систему и выгрузки
отчётов попадают в таблицу `audit_log`
(`common/interceptors/audit.interceptor.ts`). Запись выполняется до отдачи
ответа, поэтому её сбой не остаётся незамеченным. Пароли из журнала
исключаются.

**Защита от подбора паролей.** Форма входа ограничена пятью попытками в минуту
с адреса. За обратным прокси адрес берётся из `X-Forwarded-For`, иначе предел
был бы общим на всех пользователей сразу.

**Кириллица в PDF.** Штатный шрифт pdfmake не содержит русских глифов,
поэтому в отчёты встроен DejaVu Sans (`server/src/reports/fonts/`).

## Ограничения прототипа

Перечисленное ниже — осознанные упрощения, а не недоработки: каждое из них
не влияет на учебные сценарии, но должно быть названо честно.

- Интеграции с ERP, телефонией и почтой показаны на MES-диаграмме как
  окружение системы и кодом не реализованы — в ТЗ они описаны как контекст.
- Вложения к коммерческим предложениям хранятся ссылкой (`file_ref`);
  загрузка файлов в интерфейсе не реализована.
- Пользователи не удаляются, а блокируются: на них ссылаются сделки,
  активности и журнал действий.
- Курсы валют не хранятся, конвертации нет: отчёт считается по одной валюте.
- Канбан-доска работает с выборкой до 200 сделок. Если их больше, показывается
  предупреждение, что суммы по колонкам неполные, — для полной картины
  используется список с фильтрами.
- Выпадающие списки клиентов в формах ограничены 200 записями и не имеют
  серверного поиска.
- Выгрузки формируются синхронно в памяти процесса; на объёмах учебной базы
  это незаметно, но на десятках тысяч строк потребовалась бы потоковая выдача.
