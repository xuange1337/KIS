# АРМ менеджера по работе с клиентами в CRM-системе

Web-приложение для ведения клиентской базы, планирования коммуникаций и
контроля сделок отдела продаж. Реализовано по описанию прикладной программы
(Орлов Г.Н., 23ФИИТ(б)РАИС).

Приложение закрывает все пять модулей из раздела 1.2 ТЗ, пять отчётов из
раздела 2.4 и набор экранных форм из раздела 2.5.

## Технологический стек

| Слой | Реализация |
|---|---|
| Клиент | React 18 + TypeScript, Vite, MUI 6, TanStack Query, Recharts |
| Сервер | NestJS 11 + TypeORM, JWT-авторизация, ролевая модель |
| База данных | PostgreSQL 17, схема ведётся миграциями |
| Выгрузки | CSV, Excel (exceljs), PDF (pdfmake, шрифт DejaVu с кириллицей) |
| Развёртывание | Docker Compose: `db`, `api`, `web` (nginx + reverse-proxy) |
| Защита | JWT с обязательными секретами, ограничение частоты входов, журнал действий, заголовки безопасности и CSP |

## Быстрый запуск

```bash
cp .env.example .env
```

Задайте в `.env` пароль базы и два секрета подписи токенов — значений по
умолчанию у них нет, без них приложение не стартует:

```bash
printf 'JWT_ACCESS_SECRET=%s\nJWT_REFRESH_SECRET=%s\nPOSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" "$(openssl rand -hex 16)"
```

```bash
docker compose up --build -d
```

Приложение поднимется на <http://localhost:8080>. Миграции применяются
автоматически при старте контейнера `api`.

Наполнение демонстрационными данными (20 клиентов, 32 сделки, 70 активностей,
14 коммерческих предложений):

```bash
docker compose exec api node dist/database/seeds/seed.js
```

Остановка с удалением данных:

```bash
docker compose down -v
```

## Тестовые учётные записи

Демонстрационные данные создают две организации. Первая — рабочая,
вторая нужна, чтобы изоляция данных была видна, а не только заявлена.

| Роль | Логин | Пароль | Что доступно |
|---|---|---|---|
| Менеджер | `manager` | `manager123` | Только свои клиенты, сделки и активности |
| Руководитель отдела продаж | `head` | `head123` | Данные всего отдела, отчёты по сотрудникам |
| Администратор | `admin` | `admin123` | Всё перечисленное плюс управление пользователями |

Второй менеджер `manager2 / manager123` заведён, чтобы разграничение доступа
внутри организации было видно на демонстрационных данных.

Контрольная организация «ЗАО «Соседняя компания»»: `other-admin / other123`
и `other-manager / other123`. Под ними видны только их собственные клиент,
сделка, активность и КП; записи первой организации для них не существуют —
ни в списках, ни по прямой ссылке.

## Документация API

Спецификация OpenAPI собирается из самих контроллеров и DTO, поэтому не
расходится с кодом:

- интерфейс просмотра — <http://localhost:8080/api/docs>;
- машинный формат — <http://localhost:8080/api/docs/openapi.json>;
- версия в репозитории — `docs/openapi.json`, обновляется командой:

```bash
POSTGRES_HOST=localhost npm run openapi
```

Публикацию можно выключить переменной `OPENAPI_ENABLED=false`, если
развёртывание не должно раскрывать структуру API анонимно.

**Версия API** указывается в пути: `/api/v1/clients`. Прежние пути без
версии (`/api/clients`) продолжают работать — ломать уже написанных
клиентов, включая собственный интерфейс, незачем. Несовместимые
изменения контракта будут выходить следующей версией пути.

**Формат ошибки** одинаков для всех маршрутов:

```json
{
  "statusCode": 409,
  "code": "CONFLICT",
  "message": "Вместе с клиентом будут удалены связанные записи...",
  "dependents": { "contacts": 2, "deals": 0, "activities": 5 },
  "path": "/api/clients/17",
  "requestId": "0f2c6f1e-4a4d-4a5e-9c1b-2f3f1c8f0a11",
  "timestamp": "2026-09-18T07:21:41.921Z"
}
```

`message` остаётся строкой либо массивом строк для ошибок валидации,
дополнительные поля исключения сохраняются, а `requestId` совпадает с
заголовком `X-Request-Id` и с полем `requestId` в логах сервера.

## Тесты

```bash
POSTGRES_HOST=localhost npm run test:api
```

```bash
npm run test:web
```

E2E-тесты сервера покрывают авторизацию и разграничение прав,
попытки обхода доступа между менеджерами, CRUD всех модулей, переходы сделки
по стадиям с записью в историю и защиту от гонок, границы числовых значений
и удаление связанных записей, расчёт всех пяти отчётов, разделение валют,
границы периодов и выгрузку в трёх форматах. Отдельный набор
(`server/test/hardening.e2e-spec.ts`) закрепляет исправления аудита
готовности: немедленный отзыв доступа при завершении сессии, защиту
администратора от самоблокировки, устойчивый порядок страниц и маскирование
персональных данных в журнале.

Тесты работают с отдельной базой `crm_test`: она пересоздаётся и наполняется
перед каждым прогоном (`server/test/global-setup.ts`), поэтому демонстрационные
данные не портятся, а результат не зависит от порядка выполнения.

## Качество и выпуск

Одна команда прогоняет всё, что проверяется автоматически, — форматирование,
линтер, сборки, бюджет размера бандла, тесты клиента и API, лицензии,
секреты и конфигурацию compose:

```bash
POSTGRES_HOST=localhost npm run ci
```

Отдельные проверки: `npm run lint`, `npm run format`, `npm run check:bundle`,
`npm run check:secrets`, `npm run licenses:check`, `npm run audit:production`.

Проверка собранной системы целиком — сборка образов, запуск, миграции,
вход, отчёты, формат ошибки, OpenAPI и отдача SPA:

```bash
npm run smoke
```

`npm run smoke -- --clean` выполняет то же на чистых томах: данные
удаляются, база создаётся заново, миграции применяются с нуля.

Нагрузочный smoke по работающей системе (10 параллельных клиентов,
бюджет 95-го перцентиля):

```bash
npm run test:load
```

На сервере то же выполняет GitHub Actions (`.github/workflows/ci.yml`):
проверки и тесты с PostgreSQL отдельным заданием, сборка образов, smoke,
нагрузка, резервная копия и проверка восстановления — вторым.

Порядок выпуска — `docs/release-checklist.md`, история изменений —
`CHANGELOG.md`.

## Фоновые выгрузки

Выгрузка отчёта считается синхронно и целиком в памяти процесса: на
учебной базе это незаметно, но на больших выборках запрос занимает
рабочий поток на минуты, а браузер успевает разорвать соединение по
таймауту. Для таких случаев есть кнопка «В фоне» на экране отчётов и
отдельные маршруты:

| Запрос | Что делает |
|---|---|
| `POST /api/reports/:report/export/jobs?format=xlsx` | ставит задание, отвечает `202` и его идентификатором |
| `GET /api/reports/export/jobs/:id` | состояние: `pending`, `running`, `done`, `failed` |
| `GET /api/reports/export/jobs/:id/file` | готовый файл |
| `GET /api/reports/export/jobs` | последние задания пользователя |

Очередь хранится в базе: перезапуск процесса не теряет заказанные
выгрузки, а задания, брошенные в состоянии «выполняется», возвращаются
в очередь при старте. Задание захватывается условным `UPDATE` с
`FOR UPDATE SKIP LOCKED`, поэтому два экземпляра не возьмут одно и то же.
Права применяются те же, что при заказе: роль сохраняется вместе с
параметрами, и выгрузка содержит ровно тот срез данных, который видит
заказавший. Файлы хранятся сутки и удаляются вместе с записью о задании.

Синхронный маршрут `GET /api/reports/:report/export` сохранён: на выборке
в десяток строк постановка задания и опрос состояния дольше самой
выгрузки.

## Диагностика

`GET /api/diagnostics` (только администратор) отдаёт состояние
экземпляра и показатели данных: версия и время работы процесса,
занятая память, версия схемы, задержка и размер базы, число соединений,
количество клиентов, сделок, активностей, КП, пользователей, активных
сессий и записей журнала за сутки. Показатели считаются в пределах
организации: объём чужой базы администратору так же недоступен, как и
сами чужие записи.

## Принятые решения

**Изоляция организаций.** Каждая бизнес-запись принадлежит организации
(`organization_id`), и любая выборка ограничивается организацией текущего
пользователя — условие задано один раз в
`server/src/common/helpers/tenant-scope.ts` и применяется раньше проверки
ролей. Записи соседней организации отдаются как отсутствующие (404), а не
как запрещённые (403): иначе перебором идентификаторов был бы виден их
состав. Организация берётся из записи пользователя в БД, а не из токена,
поэтому перевод сотрудника действует немедленно и не подделывается.
Внешние ключи проверяют только существование записи, поэтому назначить
ответственным сотрудника другой организации отдельно запрещено проверкой.
Логин остаётся уникальным во всей системе: страница входа одна.

**Разграничение доступа.** Менеджер видит только записи, где он указан
ответственным (`owner_user_id`); руководитель и администратор — данные всего
отдела. Условие задано один раз в `server/src/common/helpers/owner-scope.ts`
и применяется всеми модулями, включая отчёты. Права на вложенные сущности
наследуются от родителя: активность нельзя привязать к чужой сделке или к
сделке другого клиента, предложение — к чужой сделке.

**Секреты.** `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` обязательны и не имеют
значений по умолчанию: приложение и `docker compose` отказываются стартовать,
пока они не заданы, и проверяют минимальную длину. Иначе токены подписывались
бы ключом, известным всем, кто видел исходники.

**Сессии.** Refresh-токены привязаны к серверным сессиям и хранятся в базе
только в виде SHA-256-хеша. При обновлении токен ротируется, повторное
использование старого токена отзывает все сессии учётной записи: отличить
кражу от гонки нельзя, а у похитителя могла остаться ещё одна выпущенная пара.
Выход, смена пароля и блокировка пользователя также отзывают сессии.
Access-токен проверяется против живой сессии, поэтому «завершить сессию»
закрывает доступ сразу, а не после истечения короткого токена. Refresh и
logout защищены CSRF-токеном, и его cookie продлевается вместе с сессией.

**Управление администраторами.** Администратор не может заблокировать себя
или снять с себя роль, а последний действующий администратор не блокируется
вовсе: восстановления пароля в системе нет, и такая операция оставила бы
систему без управления.

**История сделки.** Стадия меняется отдельной операцией
`PATCH /api/deals/:id/stage`: строка блокируется на запись, текущая стадия
читается внутри транзакции, обновление сделки и запись в `deal_stage_history`
выполняются вместе. Параллельные переводы не создают расходящихся записей.
Переход на стадию «выиграна» или «проиграна» проставляет дату закрытия,
возврат в работу — снимает её. Вероятность определяется стадией и напрямую
не редактируется.

**Удаление связанных записей.** Удаление клиента или сделки уносит по каскаду
контакты, активности, предложения и историю стадий, поэтому операция сначала
отвечает `409` с перечнем того, что будет потеряно, и выполняется только с
подтверждением: `DELETE /api/clients/:id?force=true`. Клиента со сделками
удалить нельзя вовсе — его переводят в архив.

**Светлая и тёмная схемы.** Семантические токены задаются
CSS-переменными, поэтому схема переключается переопределением переменных
на корневом элементе — без перерисовки дерева и без правки компонентов.
По умолчанию берётся системная настройка: у того, кто работает в тёмной
системе, светлый интерфейс на весь экран — это вспышка при каждом
открытии. Явный выбор сохраняется и систему перекрывает; переключатель
в нижней части меню (три состояния: как в системе, светлое, тёмное).
Тёмная схема не инверсия светлой: на тёмном фоне те же насыщенные цвета
выглядят грязными, поэтому данные и акцент осветлены отдельным набором.

**Узкие экраны.** Интерфейс рассчитан от 360 точек ширины. На телефоне
меню убирается в выдвижную панель и закрывается при переходе: свёрнутая
полоса значков занимала шестую часть ширины постоянно, на каждом экране.
Шапка экрана на узком становится в столбец — в строке подпись зажималась
в колонку шириной в два слова. Таблицы прокручиваются внутри себя, страница
по горизонтали не едет.

**Доступность.** Кроме ручной проверки контраста и фокуса, разметка
ключевых компонентов проверяется автоматически (`axe-core`,
`web/src/components/accessibility.test.tsx`): нарушения уровня serious и
critical считаются ошибкой сборки. Первая же проверка нашла настоящее:
тип активности обозначался только значком, подпись висела на `div`
атрибутом `aria-label`, который экранный диктор игнорирует. Первым в
порядке обхода клавиатурой идёт ссылка «Перейти к содержимому»: меню —
это шесть ссылок перед содержимым каждого экрана.

**Повтор потерянного запроса.** Операции создания принимают заголовок
`Idempotency-Key`. Если ответ не дошёл из-за обрыва связи и клиент
повторил запрос, возвращается результат первой попытки, а не создаётся
вторая сделка. Ключ действует в пределах учётной записи сутки; тот же
ключ с другими данными отклоняется. Заголовок необязателен.

**Одновременная правка.** Карточки клиента и сделки возвращают поле
`version` и принимают его обратно при сохранении. Если запись успели
изменить, сохранение отклоняется с 409 и текущей версией, а не затирает
чужую правку молча: раньше обе операции отвечали 200, и потерю правки
нельзя было ни заметить, ни восстановить. Поле необязательное —
клиенты API, которые его не присылают, работают как прежде.

**Порядок списков.** Сортировка списков всегда дополняется первичным ключом.
PostgreSQL не гарантирует порядок строк с одинаковым значением ключа
сортировки, и при выводе по страницам запись с распространённым значением
(сделки в одной стадии, клиенты одного статуса) попадала сразу на две
страницы, а другая не попадала никуда.

**Валюты.** Курсы в прототипе не хранятся, поэтому суммы разных валют не
складываются: денежные отчёты считаются по одной валюте (параметр `currency`,
по умолчанию рубли), а в списках и карточках сумма выводится в валюте самой
сделки.

**Версия схемы.** Экземпляр с непримененными миграциями не стартует и не
отвечает готовностью на `/api/health/ready`. Контейнер с новым кодом
иногда поднимается на старой базе: раньше он отвечал 200 и падал уже на
конкретных запросах, с частично записанными данными. Проверку снимает
`SCHEMA_CHECK=false` — чтобы подняться и выполнить миграции руками.

**Часовой пояс.** Деловой часовой пояс задаётся переменной `TZ`
(по умолчанию `Europe/Moscow`) и применяется и к серверу приложений, и к
соединению с СУБД. В нём считаются границы периодов в отчётах, группировка
по месяцам и признак просроченной активности — иначе они расходились бы с
тем, что видит пользователь.

**Трассировка и логи.** Каждому запросу присваивается идентификатор
(`X-Request-Id`); идентификатор от вышестоящего прокси сохраняется, если
состоит из безопасных символов и не длиннее 128 знаков — иначе в лог
попадали бы подделанные строки. Идентификатор возвращается в заголовке,
в теле ответа об ошибке и присутствует в каждой строке лога. В
production логи пишутся построчным JSON (`time`, `level`, `context`,
`requestId`, `userId`, `message`), в разработке — обычным текстом.

**Журналирование.** Все изменяющие запросы, входы в систему и выгрузки
отчётов попадают в таблицу `audit_log`
(`common/interceptors/audit.interceptor.ts`). Запись выполняется до отдачи
ответа. Пароли и токены в журнал не попадают, свободный текст (комментарий,
результат, адрес, контактные данные) заменяется пометкой `[скрыто]`, длинные
значения обрезаются: журнал живёт дольше самих записей и выгружается при
разборе инцидентов, поэтому хранит факт изменения, а не его содержимое.

**Защита от подбора паролей.** Форма входа ограничена пятью попытками в минуту
с адреса. За обратным прокси адрес берётся из `X-Forwarded-For`, иначе предел
был бы общим на всех пользователей сразу.

**Кириллица в PDF.** Штатный шрифт pdfmake не содержит русских глифов,
поэтому в отчёты встроен DejaVu Sans (`server/src/reports/fonts/`).

## Ограничения прототипа

Перечисленное ниже — осознанные упрощения, а не недоработки: каждое из них
не влияет на учебные сценарии, но должно быть названо честно.

- Интеграции с ERP, телефонией и почтой показаны на MES-диаграмме как
  окружение системы и кодом не реализованы — в ТЗ они описаны как контекст.
- Вложения к коммерческим предложениям хранятся ссылкой (`file_ref`);
  загрузка файлов в интерфейсе не реализована.
- Пользователи не удаляются, а блокируются: на них ссылаются сделки,
  активности и журнал действий.
- Курсы валют не хранятся, конвертации нет: отчёт считается по одной валюте.
- Канбан-доска работает с выборкой до 200 сделок. Если их больше, показывается
  предупреждение, что суммы по колонкам неполные, — для полной картины
  используется список с фильтрами.
- Выпадающие списки клиентов в формах ограничены 200 записями и не имеют
  серверного поиска.
- Выгрузки формируются синхронно в памяти процесса; на объёмах учебной базы
  это незаметно, но на десятках тысяч строк потребовалась бы потоковая выдача.
