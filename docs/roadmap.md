# План доработки до коммерческого продукта

Документ отвечает на два разных вопроса, которые часто смешивают:

1. Чего не хватает системе, чтобы считаться полноценным
   веб-приложением (продуктовая полнота).
2. Что нужно, чтобы на ней зарабатывать (подключение заказчиков,
   деньги, эксплуатация, юридическая сторона).

Второе не следует из первого: продукт может быть удобным и при этом
непродаваемым, если заказчик не может сам завести организацию, оплатить
подписку и получить поддержку.

Оценки даны в неделях для одного-двух разработчиков и означают работу
с тестами и документацией, как принято в этом репозитории, а не
«написать и забыть».

## Что уже есть (версия 1.1.0)

Это не план, а точка отсчёта: ниже перечислено только то, что
переделывать не придётся.

- Изоляция организаций на уровне данных, ролевая модель, серверные
  сессии с немедленным отзывом доступа, журнал действий с маскированием
  персональных данных.
- Контракт API: версия в пути, единый формат ошибок с идентификатором
  запроса, OpenAPI, идемпотентность создания, защита от потери правок.
- Эксплуатация: проверка версии схемы при старте, резервное копирование
  с проверяемым восстановлением, runbook аварийного восстановления,
  фоновые выгрузки, диагностика.
- Качество: 182 e2e API, 50 модульных, 28 браузерных сценариев, CI с
  прогоном на собранных образах, бюджет размера сборки, проверка
  секретов и лицензий.
- Пять модулей ТЗ и шесть отчётов, поиск по всем разделам, массовые
  операции, загрузка базы из файла, причины проигрыша, светлая и тёмная
  схемы, работа от 360 точек ширины.

## Этап 1. Заказчик подключается сам — 2–3 недели

Сейчас организация заводится запросом в базу, а сотрудники —
администратором вручную. Пока это так, каждый новый заказчик требует
участия разработчика, и продавать систему нельзя даже за наличные.

| Задача | Почему это блокирует продажу |
|---|---|
| API и интерфейс управления организациями | без них подключение — ручная операция в базе |
| Membership: пользователь в нескольких организациях, роль в рамках организации | партнёр или консультант обслуживает несколько клиентов; сейчас роль лежит в самой учётной записи |
| Переключение организации в интерфейсе | следствие предыдущего пункта |
| Приглашения по одноразовой ссылке | иначе администратор придумывает и диктует пароли, как было до версии 1.1.0 |
| Транзакционная почта (SMTP) с шаблонами | приглашения и восстановление пароля сейчас передаются из рук в руки |
| Самостоятельная регистрация и пробный период | без неё воронка продаж упирается в менеджера |

**Техническое следствие:** роль переезжает из `users` в
`organization_members`, это миграция и правка каждого места, где
сейчас читается `user.role`, плюс межтенантные проверки заново.
Отложить нельзя: чем позже, тем дороже.

## Этап 2. Деньги — 3–4 недели

| Задача | Содержание |
|---|---|
| Тарифы и лимиты | число пользователей, записей, размер файлов; лимит проверяется в коде, а не только на витрине |
| Подписки | пробный период, продление, смена тарифа с пересчётом, отмена |
| Приём платежей | ЮKassa или CloudPayments: оплата, вебхуки о статусе, идемпотентность уведомлений, повторные попытки |
| Счета и закрывающие документы | счёт, акт, УПД; для юридических лиц это обязательное условие покупки |
| НДС и чеки | 54-ФЗ: фискальный чек через оператора, иначе оплату от физлица принимать нельзя |
| Поведение при неоплате | предупреждения, блокировка записи данных с сохранением чтения и выгрузки — удалять данные за неуплату нельзя |
| Административная панель оператора | кто, на каком тарифе, когда платил, ручная корректировка |

**Совет по очерёдности:** первым двум-трём заказчикам можно выставлять
счета вручную и не писать биллинг вовсе. Автоматизировать имеет смысл,
когда ручная выписка станет занимать больше времени, чем разработка.

## Этап 3. Продуктовая полнота — 4–6 недель

То, отсутствие чего заметит любой, кто сравнивает систему с
Битрикс24 или amoCRM.

| Задача | Оценка | Замечание |
|---|---|---|
| Файловое хранилище вложений (S3-совместимое) | 1 нед | сейчас у предложения только ссылка; нужны загрузка, проверка типа и размера, вирус-скан или хотя бы белый список |
| Каталог товаров и услуг, позиции сделки и КП | 1–1,5 нед | сумма перестанет вводиться руками и начнёт считаться из позиций |
| Шаблоны документов (счёт, КП в PDF) | 1 нед | продолжение предыдущего пункта; инфраструктура PDF уже есть |
| Теги и сегменты | 0,5 нед | |
| Пользовательские поля | 1–1,5 нед | требует продуманной модели: `jsonb` с описанием схемы в отдельной таблице |
| Несколько воронок | 1 нед | стадии становятся настраиваемыми; затрагивает отчёты |
| Дедупликация и объединение карточек | 1 нед | импорт сейчас только отбраковывает дубли |
| Центр уведомлений | 1 нед | напоминания о встречах и просрочках в интерфейсе и на почту |
| Комментарии, подзадачи, чек-листы | 0,5 нед | |
| Сохранённые фильтры и представления | 0,5 нед | |
| Повторяющиеся активности | 0,5 нед | |

## Этап 4. Эксплуатация под нагрузкой — 2–3 недели

Сегодняшние ограничения честно перечислены в
`docs/production-readiness.md`. Самые существенные:

| Задача | Что исправляет |
|---|---|
| Непрерывное архивирование WAL и восстановление на момент времени | сейчас допустимая потеря данных — сутки (RPO); для платного сервиса это много |
| Автоматическая выгрузка копий во внешнее хранилище | копия на том же хосте не защищает от его потери |
| Выкатка без простоя | сейчас обновление требует короткого простоя: код несовместим со старой схемой |
| Метрики (Prometheus) и алерты | диагностика есть, но никто не разбудит дежурного ночью |
| Логи во внешний сборщик | `requestId` уже сквозной, но логи живут в контейнере |
| Полнотекстовый поиск (`pg_trgm`/`tsvector`) | поиск по `LIKE` перестанет держать нагрузку на сотнях тысяч записей |
| Нагрузочное тестирование на реальных объёмах | текущий smoke проверяет 200 запросов на учебной базе |
| Optimistic locking для остальных сущностей | сейчас защищены только клиенты и сделки |

## Этап 5. Безопасность и соответствие — 2–3 недели

| Задача | Замечание |
|---|---|
| Двухфакторная проверка (TOTP) и коды восстановления | обычное требование корпоративного заказчика |
| Вход через внешние системы (SSO) | для заказчиков от полусотни сотрудников |
| Политики хранения и права субъекта персональных данных | выгрузка и удаление по запросу; без этого 152-ФЗ и GDPR не закрыть |
| Согласие на обработку, ToS, политика конфиденциальности, cookie | текст пишет юрист, но интерфейс и хранение согласий — разработка |
| Размещение персональных данных на территории РФ, уведомление РКН | требование 152-ФЗ к оператору; влияет на выбор площадки |
| Внешний аудит или пентест | перед продажей корпоративному заказчику |

**Важно:** соответствие закону — свойство конкретного развёртывания и
договора, а не кода. Код может сделать соответствие возможным, но не
обеспечивает его сам по себе. Заявлять его без юридической оценки
нельзя.

## Этап 6. Зрелость интерфейса — 2 недели

| Задача | Замечание |
|---|---|
| Сквозная клавиатурная навигация | проверена выборочно; нужен обход всех экранов и модальных окон |
| Состояния загрузки, ошибки, пустоты, потери сети | частично есть; нет единого поведения при обрыве связи |
| Onboarding и встроенная справка | первый экран нового заказчика сейчас пустой |
| Вычитка тёмной схемы в редких состояниях | формы с ошибками, пустые отчёты |
| Vendor splitting сборки | основной чанк у верхней границы бюджета |

## Этап 7. Поддержка и запуск — 1–2 недели

- Канал поддержки и регламент ответа (SLA), журнал обращений.
- Страница состояния сервиса.
- Демонстрационный стенд с данными, который не стыдно показать.
- Обучающие материалы: короткое видео и сценарии «первые 15 минут».
- Процедура переноса данных заказчика (импорт уже есть, нужен регламент).

## Сводная оценка

| Этап | Недели | Можно ли отложить |
|---|---|---|
| 1. Самостоятельное подключение | 2–3 | нет, блокирует продажу |
| 2. Деньги | 3–4 | да, если первых клиентов вести по счетам вручную |
| 3. Продуктовая полнота | 4–6 | частично: порядок задач зависит от того, кому продаёте |
| 4. Эксплуатация под нагрузкой | 2–3 | нет, если обещаете доступность |
| 5. Безопасность и соответствие | 2–3 | нет для корпоративного заказчика |
| 6. Зрелость интерфейса | 2 | да |
| 7. Поддержка и запуск | 1–2 | нет |

**Итого 16–23 недели** работы одного-двух разработчиков, то есть
примерно 4–6 месяцев до состояния, в котором систему можно продавать
не единственному знакомому заказчику.

## Минимальный путь до первого платящего клиента

Если задача — не «сделать всё», а получить первую выручку, достаточно
значительно меньшего. Порядок такой:

1. **Этап 1 целиком** — иначе каждое подключение делает разработчик.
2. **Из этапа 4**: внешние копии и алерты. Потерять данные платящего
   заказчика — конец истории, а не инцидент.
3. **Из этапа 3**: вложения и позиции КП — первое, о чём спрашивают.
4. **Из этапа 5**: ToS, политика конфиденциальности, согласие на
   обработку. Без них нельзя даже собирать регистрации.
5. **Счета вручную**, биллинг позже.

Это 5–7 недель вместо полугода. Остальное добавляется по мере того, как
заказчики объясняют, чего им не хватает, — и это более надёжный
источник приоритетов, чем список выше.

## Чего в плане намеренно нет

- Мобильного приложения: интерфейс работает от 360 точек, нативное
  приложение окупается после нескольких сотен активных пользователей.
- Телефонии, почтовой интеграции и обмена с 1С: это не одна задача, а
  отдельное направление с собственным сопровождением. Браться имеет
  смысл под конкретного заказчика, который за это платит.
- Искусственного интеллекта в любом виде: пока в системе нет объёма
  данных, на котором он даёт пользу.
