# Руководство администратора

Документ описывает установку, эксплуатацию и восстановление системы.
Работа с клиентами и сделками — в `docs/user-guide.md`.

## Установка

Требуется Docker с плагином Compose.

```bash
cp .env.example .env
```

Заполните в `.env` пароль базы и два секрета подписи токенов — значений
по умолчанию у них нет, без них система не стартует:

```bash
printf 'JWT_ACCESS_SECRET=%s\nJWT_REFRESH_SECRET=%s\nPOSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" "$(openssl rand -hex 16)"
```

```bash
docker compose up --build -d
```

Приложение поднимется на <http://localhost:8080>; миграции применяются
автоматически. Наполнение демонстрационными данными (для показа, не для
рабочего стенда):

```bash
docker compose exec api node dist/database/seeds/seed.js
```

## Настройки

| Переменная | Назначение |
|---|---|
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | секреты подписи токенов, обязательны, не менее 32 символов |
| `POSTGRES_PASSWORD` | пароль базы, обязателен |
| `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` | срок жизни токенов (`15m`, `7d`) |
| `COOKIE_SECURE` | `true` при работе по HTTPS |
| `LOGIN_RATE_LIMIT` | попыток входа в минуту с адреса; за одним NAT сидит весь офис, поэтому на больших стендах предел поднимают |
| `BODY_LIMIT` | предел размера тела запроса |
| `UPLOADS_DIR` | каталог вложений и готовых выгрузок |
| `SCHEMA_CHECK` | проверка версии схемы при старте; `false` только чтобы починить схему руками |
| `OPENAPI_ENABLED` | публикация описания API на `/api/docs` |
| `TZ` | деловой часовой пояс; в нём считаются границы периодов в отчётах |

Смена секретов подписи закрывает все активные сеансы — это штатный
способ разом отозвать доступ.

## Пользователи и доступ

Раздел «Пользователи» доступен администратору. Роли:

- **менеджер** — свои клиенты, сделки и активности;
- **руководитель** — данные всего отдела, отчёты по сотрудникам,
  назначение ответственных, загрузка базы из файла;
- **администратор** — всё перечисленное плюс управление учётными
  записями.

Пользователи не удаляются, а блокируются: на них ссылаются сделки,
активности и журнал действий. Заблокировать последнего действующего
администратора или снять права с самого себя система не даст —
восстановить доступ было бы нечем.

**Забытый пароль.** Кнопка с ключом в строке пользователя выдаёт
одноразовую ссылку. Передайте её сотруднику; пароль он задаст сам, вам
он известен не будет. Ссылка живёт сутки и срабатывает один раз.

## Организации

Каждая бизнес-запись принадлежит организации, и выборки ограничены
организацией текущего пользователя. Организации заводятся миграцией и
наполнением; интерфейса управления ими пока нет — при подключении
второго заказчика организация добавляется запросом в базу, а
пользователи заводятся в ней обычным порядком.

## Резервное копирование

```bash
BACKUP_DIR=/srv/crm-backups npm run backup
```

Копия содержит дамп базы, вложения, версию схемы и контрольные суммы.
`BACKUP_PASSPHRASE` включает шифрование, `BACKUP_KEEP_DAYS` — срок
хранения. Настройте ежедневный запуск и **еженедельную проверку**:

```bash
npm run restore -- /srv/crm-backups/<копия> --verify
```

Проверка восстанавливает копию в отдельную базу и сверяет содержимое —
непроверенная копия не считается копией. Каталог копий обязан уезжать
на другой носитель: копия на том же диске не защищает от отказа диска.

Порядок действий при аварии, полной потере хоста и неудачном
обновлении — `docs/runbook-disaster-recovery.md`.

## Обновление

1. Снимите копию и проверьте её.
2. `git pull && docker compose up --build -d`.
3. Убедитесь: `curl -s <хост>/api/health/ready` отдаёт
   `{"status":"ok","database":"up","schema":"current"}`.

Экземпляр с непримененными миграциями не стартует и не считается
готовым — это защита от запуска нового кода на старой базе. Полный
список шагов — `docs/release-checklist.md`.

## Наблюдение за системой

- `/api/health/live` — процесс жив; `/api/health/ready` — готов принимать
  трафик (база доступна, схема актуальна).
- `/api/diagnostics` (администратор) — версия и время работы процесса,
  занятая память, размер и задержка базы, число соединений, объёмы
  данных организации, активные сессии, записи журнала за сутки.
- Логи в production — построчный JSON с идентификатором запроса
  (`requestId`). Тот же идентификатор возвращается пользователю в
  ответе об ошибке: по нему находится вся цепочка.
- Журнал действий (`audit_log`) хранит изменяющие операции, входы и
  выгрузки. Персональные данные из свободного текста в него не
  попадают: хранится факт изменения, а не содержимое.

## Что система не делает

- Не рассылает почту: ссылки и уведомления передаются вручную.
- Не хранит курсы валют: отчёты считаются по одной валюте.
- Не принимает файлы вложений: у предложения хранится ссылка.
- Не поддерживает вход через внешние системы (SSO) и двухфакторную
  проверку.
