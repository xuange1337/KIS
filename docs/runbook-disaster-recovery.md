# Runbook: резервное копирование и восстановление

Документ описывает, что делать до аварии и во время неё. Все команды
выполняются из корня репозитория на хосте, где поднят `docker compose`.

## Что защищаем

| Данные | Где лежат | Чем снимаются |
|---|---|---|
| База PostgreSQL | том `db-data` | `pg_dump -Fc` через контейнер `db` |
| Вложения | том `uploads` | `tar` через контейнер `api` |
| Версия схемы | таблица `migrations` | `schema-version.txt` в копии |
| Секреты (`.env`) | файл на хосте | **в копию не входят**, хранятся отдельно |

Секреты намеренно не попадают в резервную копию: копия уезжает на другой
носитель, и утечка её файла не должна означать утечку ключей подписи
токенов. Без `.env` база бесполезна для постороннего, но и восстановление
без него невозможно — храните его в менеджере секретов.

## Целевые показатели

| Показатель | Значение | Чем обеспечивается |
|---|---|---|
| RPO (допустимая потеря данных) | 24 часа | ежесуточная копия |
| RTO (время восстановления) | 30 минут | проверенная процедура ниже |
| Срок хранения | 14 дней | `BACKUP_KEEP_DAYS` |

Для меньшего RPO нужен WAL-архив (`archive_command` и непрерывное
архивирование) — в текущей конфигурации его нет, и заявлять RPO меньше
суток нельзя.

## Ежедневная копия

```bash
BACKUP_DIR=/srv/crm-backups BACKUP_KEEP_DAYS=14 scripts/backup.sh
```

Копия шифруется, если задана парольная фраза:

```bash
BACKUP_PASSPHRASE="$(cat /srv/secrets/backup.pass)" scripts/backup.sh
```

Расписание (cron, ежедневно в 03:15):

```bash
15 3 * * * cd /srv/crm && BACKUP_DIR=/srv/crm-backups scripts/backup.sh >> /var/log/crm-backup.log 2>&1
```

Копия каждую ночь кладётся в каталог вида `20260919-031500` и содержит
`database.dump`, `uploads.tar`, `schema-version.txt` и `SHA256SUMS`.
Каталог обязан уезжать на отдельный носитель или в объектное хранилище:
копия на том же диске не защищает от отказа диска.

## Еженедельная проверка восстановления

Непроверенная копия не считается копией. Проверка восстанавливает дамп в
отдельную базу `restore_check`, сверяет контрольные суммы, считает строки
и сравнивает версию схемы:

```bash
scripts/restore.sh /srv/crm-backups/20260919-031500 --verify
```

Расписание (по понедельникам в 04:00):

```bash
0 4 * * 1 cd /srv/crm && scripts/restore.sh "$(ls -d /srv/crm-backups/* | tail -1)" --verify >> /var/log/crm-restore-check.log 2>&1
```

Ненулевой код возврата — повод для тревоги: копии за эту неделю
непригодны, и восстановить систему из них не получится.

## Восстановление после аварии

1. **Оценить потерю.** Работает ли база: `docker compose ps`,
   `curl -s localhost:8080/api/health/ready`. Если ответ
   `schema` не `current` — проблема в версии схемы, а не в данных,
   см. раздел «Неудачное обновление».
2. **Остановить приложение**, чтобы оно не писало в повреждённую базу:
   `docker compose stop api web`.
3. **Выбрать копию** — последнюю, прошедшую проверку.
4. **Проверить её отдельно**, прежде чем трогать рабочую базу:
   `scripts/restore.sh <копия> --verify`.
5. **Восстановить рабочую базу** (запросит подтверждение — имя базы):
   `scripts/restore.sh <копия> --production`.
6. **Поднять приложение**: `docker compose up -d`.
7. **Убедиться**: `curl -s localhost:8080/api/health/ready` отдаёт
   `{"status":"ok","database":"up","schema":"current"}`; вход в интерфейс
   работает; в списке клиентов ожидаемое число записей.
8. **Записать в журнал инцидента**: время аварии, использованная копия,
   объём потерянных данных (от времени копии до времени аварии).

## Полная потеря хоста

```bash
git clone <репозиторий> /srv/crm && cd /srv/crm
cp /srv/secrets/.env .env            # секреты из менеджера секретов
docker compose up -d db              # база поднимается пустой
scripts/restore.sh /srv/crm-backups/<копия> --production
docker compose up -d
```

Миграции при старте `api` применяются автоматически; если копия старше
текущего кода, они доведут схему до актуальной. Обратной совместимости
кода со старой схемой нет, поэтому запускать новый код на старой базе без
миграций нельзя — проверка версии схемы не даст этого сделать.

## Неудачное обновление

Экземпляр с непримененными миграциями не стартует и не отвечает
готовностью. Порядок действий:

1. `docker compose logs api --tail 50` — в логе будет имя последней
   применённой миграции и текст о расхождении.
2. Применить миграции вручную:
   `docker compose exec api node -e "require('./dist/database/data-source')"`
   либо на хосте: `POSTGRES_HOST=localhost npm run migration:run -w @crm/server`.
3. Если миграция не применяется — откатить релиз на предыдущий образ и
   восстановить базу из копии, снятой до обновления. Снимать копию
   непосредственно перед обновлением обязательно.
4. Временно снять проверку (`SCHEMA_CHECK=false`) допустимо только чтобы
   поднять экземпляр и починить схему руками, не для работы под нагрузкой.

## Чего в процедуре нет

- Непрерывного архивирования WAL и восстановления на момент времени (PITR).
- Автоматической выгрузки копий во внешнее хранилище: каталог копий
  отправляется наружу средствами хоста и это вне репозитория.
- Репликации и горячего резерва: отказ базы означает простой на время
  восстановления.
