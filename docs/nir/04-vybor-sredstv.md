# Обоснование инструментальных и вычислительных средств

## Критерии выбора

Выбор определяется задачами АРМ: многопользовательская работа через браузер, согласованное хранение взаимосвязанных записей, проверка прав, формирование отчётов, воспроизводимое развёртывание и сопровождение. Дополнительное условие проекта — отсутствие обязательных платных внешних сервисов. Использование бесплатных компонентов не устраняет расходы на сервер, резервные копии и труд администратора.

Рассматривается уже реализованный прототип, поэтому выбор оценивается также по возможности проверить решения в существующем коде. Не утверждается, что выбранный стек превосходит все альтернативы. Критерии — соответствие требованиям и соразмерность учебному проекту.

## Архитектурный подход

Выбрана веб-архитектура с отдельным интерфейсом и модульным сервером. Пользователю нужен браузер; данные и правила доступа централизованы. Сервер реализован как модульный монолит: подсистемы разделены в коде, но развёртываются одним процессом. Это позволяет выполнять связанные изменения в одной базе и уменьшает число компонентов эксплуатации.

Альтернатива — микросервисы — добавила бы распределённые транзакции, обмен сообщениями и дополнительные узлы наблюдения. Для текущего объёма предметной области эти расходы не обоснованы измеренной потребностью. Серверный рендеринг также возможен, но отдельный SPA удобен для интерактивных карточек, календаря и канбана. Преимущество по скорости не заявляется без сравнения.

## Программные средства

| Средство в проекте | Основание выбора | Альтернатива и компромисс |
|---|---|---|
| TypeScript | Статические типы и общие перечисления клиента и сервера; помогает выявлять несовместимые обращения при сборке [Т1] | JavaScript проще по настройке, но не обеспечивает такую же проверку типов |
| React 18 и Vite | Компоненты повторно используются в списках, карточках и формах; отдельная сборка интерфейса [Т2] | Vue или Angular также подходят; сравнение скорости разработки не проводилось |
| MUI, React Hook Form, Zod | Общие элементы интерфейса, управление вводом и клиентская проверка форм | Собственная библиотека увеличивает объём сопровождения; проверка в браузере не заменяет серверную |
| TanStack Query | Управление загрузкой, обновлением и инвалидированием серверных данных | Ручное управление запросами требует поддерживать те же состояния самостоятельно |
| NestJS 11.2.5 | Модули, внедрение зависимостей, контроллеры и guards соответствуют выделенным подсистемам [Т3] | Express без каркаса оставляет больше архитектурных решений разработчику |
| TypeORM | Отображение сущностей и последовательные миграции схемы | Прямой SQL даёт явный контроль, но требует отдельного слоя отображения; сложные отчёты всё равно требуют анализа SQL |
| PostgreSQL 17 | Внешние ключи, ограничения, транзакции и точные денежные типы соответствуют связанной модели CRM [Т4, Т5] | SQLite подходит для простых локальных сценариев; документная БД потребовала бы иначе обеспечивать связи |
| Nodemailer | Исходящая почта по SMTP (приглашения, подтверждение адреса, напоминания о пробном периоде); сервер не привязан к конкретному провайдеру | Почтовый API провайдера проще в настройке, но делает работу зависимой от внешнего сервиса |
| ExcelJS | Разбор файлов импорта клиентов и выгрузка отчётов в xlsx без внешнего сервиса | Только CSV проще, но неудобен менеджеру; тяжёлые выгрузки выполняются фоновыми заданиями |
| Собственный реестр метрик, pg_trgm | Метрики в текстовом формате Prometheus без дополнительной библиотеки; триграммные индексы для подстрочного поиска средствами PostgreSQL | Готовая библиотека метрик и внешний поисковый движок добавили бы зависимости; выигрыш индекса по времени не измерен (проверен только выбор индекса планировщиком) |
| Docker Compose и nginx | Описание узлов БД, API и интерфейса; одинаковые команды запуска и проксирование API [Т6] | Установка на хост возможна, но увеличивает зависимость от его конфигурации |
| Jest/Supertest, Vitest, Playwright | Проверка API, компонентов и браузерных сценариев | Ручная проверка остаётся необходимой для пользовательской пригодности |

Версии прямых зависимостей на 26.10.2026 соответствуют таблице: NestJS 11.2.5, TypeORM 0.3, React 18.3, Vite 6, MUI 6, Zod 3, Vitest 3, Jest 29, TypeScript 5.9, PostgreSQL 17 (`postgres:17-alpine`), nginx 1.27. Использован менеджер пакетов npm с lock-файлом.

Node.js является средой исполнения сервера и инструментов сборки. Dockerfile использует Node.js 22; требование репозитория — Node.js 20 и выше. Фактические версии конкретного эксперимента фиксируются отдельно. Версии из заголовков документации не заменяют версии lock-файла проекта.

JWT используется вместе с серверными сессиями и проверкой участия пользователя в организации. Один токен не считается достаточным доказательством актуальных прав. Refresh-токен передаётся в HttpOnly cookie, в базе хранится его хеш. Ротация, отзыв и CSRF-защита реализованы в модуле аутентификации.

## Вычислительные средства

Система использует три логических узла: PostgreSQL, API и nginx с собранным интерфейсом. В локальном исследовательском стенде они работают в Docker на одном компьютере. Вычислительные ресурсы совместно используются базой, приложением и генератором нагрузки; результаты такого стенда нельзя переносить на промышленный сервер без повторного измерения.

Расчёт потребности включает объём данных и индексов, вложения, резервные копии, число одновременно работающих сотрудников и тяжёлые отчёты. В работе не задаётся неподтверждённый минимум CPU/RAM как гарантия производительности. Фактический процессор, память хоста и Docker, версии образов, число клиентов нагрузки и объём данных фиксируются в [экспериментальной части](experiment-plan.md).

Для эксплуатации требуется место как для действующих данных, так и для резервной копии и проверочного восстановления. Внешние интеграции не входят в стенд; синтетические данные не требуют обработки реальных персональных сведений. Переход к реальному использованию потребует отдельно обеспечить HTTPS, хранение секретов, резервирование и эксплуатационные регламенты.

## Вывод

Выбранные средства соответствуют модели АРМ с централизованными данными, интерактивным интерфейсом и едиными правилами доступа. Модульный монолит уменьшает число эксплуатационных зависимостей; реляционная БД позволяет выразить связи и выполнять составные операции транзакционно; контейнеризация задаёт воспроизводимый способ запуска. Ограничения решения проверяются экспериментально, а статическая типизация и ORM не рассматриваются как гарантия отсутствия ошибок.
